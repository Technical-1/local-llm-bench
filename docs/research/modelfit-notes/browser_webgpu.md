# Browser local AI: how fit is decided, and detecting GPU memory from a web page (as of October 2026)

Method note: sources are the WebGPU spec (W3C TR), gpuweb GitHub issues, Chromium source read directly from chromium.googlesource.com (main branch, fetched 2026-10-18), shallow clones of mlc-ai/web-llm (last commit 2026-10-11) and huggingface/transformers.js (last commit 2026-10-06), Chrome developer docs, blink-dev, and academic papers. Chromium bug tracker pages need sign-in, so two crbug details come from search snippets and are marked as such. About 20 tool calls were used.

## 1. What WebGPU exposes (adapter info, limits, memory proposals) and per-browser status

### Takeaway
The standard API exposes no memory capacity at all. GPUAdapterInfo gives vendor/architecture/device/description strings (which browsers may leave empty), subgroup sizes and isFallbackAdapter. Limits like maxBufferSize cap single allocations, not total memory. Chrome has a non-standard `memoryHeaps` field, but only behind a developer flag. The working group has twice declined a memory-capacity API (Jan 2026 and Sep 2026) and instead **recommends trial allocations**, which is the modelfit plan.

### Cited Findings
- The GPUAdapterInfo IDL has readonly `vendor`, `architecture`, `device`, `description` (DOMString), `subgroupMinSize`, `subgroupMaxSize` (unsigned long) and `isFallbackAdapter` (boolean). "If no value is provided, the attribute will return the empty string", and for privacy the UA may set e.g. vendor to "the empty string or a reasonable approximation." — [WebGPU spec, W3C TR](https://www.w3.org/TR/webgpu/)
- Spec privacy text: "When adapter identifiers are exposed by default they should be as broad as possible while still being useful"; the UA "will always have the discretion to not report adapter identifiers at all"; and "the user can be asked for consent to reveal additional information about their hardware." UAs "are not obligated to expose the real hardware limits", and one suggested strategy is "binning all the target platforms into a few number of bins." — [WebGPU spec §2.2](https://www.w3.org/TR/webgpu/)
- Spec §2.1.11 (memory resources): "WebGPU exposes fallible allocations from machine-global memory heaps, such as VRAM" and "When a heap is depleted, WebGPU would fail to create a resource." The spec treats this as a known security/privacy consideration. — [WebGPU spec](https://www.w3.org/TR/webgpu/)
- Default limits: `maxBufferSize` = 268435456 bytes (256 MiB); `maxStorageBufferBindingSize` = 134217728 bytes (128 MiB). Apps must request higher values with `requiredLimits` up to `adapter.limits`. — [WebGPU spec](https://www.w3.org/TR/webgpu/)
- Chrome (Blink `gpu_adapter.cc`): adapter info is built from Dawn's info (`architecture_`, `description_ = info.device`, `driver_ = info.description`). Only when `RuntimeEnabledFeatures::WebGPUDeveloperFeaturesEnabled()` is on does Chrome "provide all available" info (device, description, driver, and so on). Otherwise it returns only vendor, architecture, subgroup sizes and isFallbackAdapter. So by default Chrome exposes vendor plus a coarse architecture family (e.g. "ampere", "rdna-3"), and `device`/`description` are empty. — [Chromium source: third_party/blink/renderer/modules/webgpu/gpu_adapter.cc](https://chromium.googlesource.com/chromium/src/+/main/third_party/blink/renderer/modules/webgpu/gpu_adapter.cc)
- Chrome's non-standard `GPUAdapterInfo.memoryHeaps` "exposes ... the size and type of memory heaps available on the adapter". It sits on the "WebGPU developer features" page, which needs `chrome://flags/#enable-webgpu-developer-features`. The same page lists `d3dShaderModel`, `vkDriverVersion` and `powerPreference`, and turns off timestamp quantization. The docs do not say outright that memoryHeaps is flag-gated, but the Blink code above returns the extended info only under that flag. — [Chrome for Developers: WebGPU developer features](https://developer.chrome.com/docs/web-platform/webgpu/developer-features); [gpu_adapter.cc](https://chromium.googlesource.com/chromium/src/+/main/third_party/blink/renderer/modules/webgpu/gpu_adapter.cc)
- gpuweb #5505, "Support for querying maximum/available GPU memory" (Reese Levine, 2026-01-08; open, milestone "Milestone 4+"). It asked for coarse thresholds built on Metal `recommendedMaxWorkingSetSize`, Vulkan memory heaps / `VK_EXT_memory_budget`, and DXGI. Kai Ninomiya replied that the Device Memory API "is non-standard (Chromium-only)", that "total available memory is not really well defined" because VRAM can page to RAM or disk, and pointed to the existing `"out-of-memory"` error from createBuffer/createTexture as the mechanism, plus a possible "weak" allocation library. The filer answered that he could infer memory from failed allocations: "Really, this is just a sidestep around the security issues in the spec." — [gpuweb #5505](https://github.com/gpuweb/gpuweb/issues/5505)
- gpuweb #6957, "Coarse 'available memory' signal on GPUAdapter for capacity planning" (filed 2026-08-26 by hemanth; **closed as not planned 2026-09-24** by kainino0x). It proposed `adapter.memoryClass` = low/medium/high, or a budget rounded to 1-2 GB. The filer's current workaround is exactly modelfit's probe: "allocate `STORAGE` buffers in a loop under an `out-of-memory` error scope until one fails", then sum and destroy. He notes it "stalls the main thread" and pressures the GPU, and argues "a probe that walks the GPU to OOM leaks more than a bucketed number would." Maintainer advice: (a) allocate the needed resources *before* downloading and touch them so they are committed (less sensitive to fragmentation and other apps; see related #6968), and (b) use trial allocations to estimate capacity, because an "available memory" number cannot account for fragmentation or for how many buffers a model needs at once. He acknowledged results can change between probe and real allocation. — [gpuweb #6957](https://github.com/gpuweb/gpuweb/issues/6957)
- Older context: gpuweb #2195 on how much hardware info to expose (it proposed a consent-gated debug-info method), and #1371 on the maxBufferSize limit. — [gpuweb #2195](https://github.com/gpuweb/gpuweb/issues/2195); [gpuweb #1371](https://github.com/gpuweb/gpuweb/issues/1371)
- Shipping status: Chrome/Edge 113+ on Windows (D3D12), macOS and ChromeOS; Android in Chrome 121+ (Android 12+, Qualcomm/ARM GPUs). Firefox 141 on Windows (July 2025) and 145 on Apple Silicon macOS (Nov 2025); Firefox Linux, Android and Intel Macs were "in progress" as of Nov 2025. Safari 26 on macOS Tahoe 26, iOS 26, iPadOS 26 and visionOS 26. — [web.dev: WebGPU is now supported in major browsers](https://web.dev/blog/webgpu-supported-major-browsers)
- Khronos SIGGRAPH 2026 deck: Chromium added Linux support for Intel Gen12+ GPUs in 2026-01 and a Compatibility Mode for older Android (GLES 3.1) in 2026-02. — [Khronos WebGL & WebGPU SIGG26](https://www.khronos.org/developers/linkto/webgl-and-webgpu-sigg26) (seen via search summary only; not opened)

### Inferences
- Hint data available to modelfit by default: vendor plus architecture family (Chrome), feature flags (`shader-f16`, subgroups), the limits, and isFallbackAdapter (a software adapter, so treat it as no GPU). Device name and VRAM size are not available by default in any browser I could confirm.
- `maxBufferSize`/`maxStorageBufferBindingSize` vary by device and backend, so they work as a coarse device-class signal (web-llm uses maxStorageBufferBindingSize < 1 GB to "guess whether the device has limited resources like an Android phone"; see §3). They are not a capacity measure.
- The probing allocator lines up with what the spec editor himself recommends. Combining it with the "pre-allocate before download" pattern from #6957/#6968 is the most robust design: probe for menu-level ranking, then really allocate the chosen model's buffers before fetching weights.

### Gaps
- Exact per-browser adapter-info output for Safari 26 and Firefox (what `architecture`/`vendor` strings they return, and whether they bucket limits) is not confirmed from WebKit or Gecko source. Only a low-quality blog claims Safari abstracts Apple GPU naming. This needs measuring on real machines (webgpureport.org dumps would work).
- Whether Chrome reports *tiered/bucketed* limits by default (vs. raw adapter limits) was not confirmed from source.
- I could not see the status of gpuweb #6968 (allocate-before-download).

## 2. Browser behaviour on over-allocation, caps, and unified vs discrete memory

### Takeaway
By spec, a failed allocation does **not** throw. createBuffer returns an invalid object and raises a `GPUOutOfMemoryError`, which an `out-of-memory` error scope catches. In practice, Chrome on Windows D3D12 has been seen to **lose the device or the whole GPU connection instead of returning OOM**. On Android, too many buffers has crashed the browser. Lazy commit and paging mean an allocation can "succeed" without the memory being resident. So the probe's ceiling is noisy and its failure mode is not always graceful.

### Cited Findings
- Spec: objects are invalid from creation if "there is not enough memory to allocate a resource". In createBuffer, "If the allocation fails without side-effects, generate an out-of-memory error". If an operation fails "with side effects that would observably change the state of objects on the device", the device "should be lost". UAs should consider "developer-visible warnings" for losses the app did not start. The `mappedAtCreation` size check throws a RangeError, which is a validation error, not an OOM. — [WebGPU spec](https://www.w3.org/TR/webgpu/)
- WebGPU explainer: a failed createBuffer returns an invalid object and generates an out-of-memory error catchable with `pushErrorScope('out-of-memory')`. Device loss is a separate path that can come from unrecoverable OOM or a GPU process crash. — [WebGPU Explainer](https://gpuweb.github.io/gpuweb/explainer/)
- Chromium issue 40941407, "Receive GPU connection lost instead of GPUOutOfMemoryError": exhausting VRAM gave device/GPU-connection loss instead of OOM, reproduced from M114 on the Windows D3D12 backend and tied to crbug.com/dawn/1435. Linux behaved correctly. — [crbug 40941407](https://issues.chromium.org/issues/40941407) (details from a search snippet; the page needs sign-in, current status unverified)
- Chromium issue 41492442, "Chrome on Android crashes when creating too many buffers with WebGPU": a Dawn error ("Failed to allocate memory for buffer mapping") fired once accumulated size reached about 31.75 GB on desktop. A commenter asked whether memory-pressure signals could make createBuffer fail cleanly. Marked obsolete. — [crbug 41492442](https://issues.chromium.org/issues/41492442) (search snippet only)
- Spec editor on #5505: total available memory "is not really well defined" because VRAM pages can be swapped to RAM or disk. On #6957 he recommended "touching" pre-allocated memory so it is committed. That implies an untouched createBuffer may not be backed by resident memory. — [gpuweb #5505](https://github.com/gpuweb/gpuweb/issues/5505); [gpuweb #6957](https://github.com/gpuweb/gpuweb/issues/6957)
- On macOS, Chrome's own comment says "Mac doesn't allow directly querying VRAM, and instead returns the 'recommended' maximum VRAM to use, which may change depending on system load" (Metal `recommendedMaxWorkingSetSize`). For integrated GPUs Chrome assumes they "can use at least 1/2 of system RAM as VRAM". — [Chromium source: services/on_device_model/ml/performance_class.cc](https://chromium.googlesource.com/chromium/src/+/main/services/on_device_model/ml/performance_class.cc)

### Inferences
- A probe must handle three outcomes: (1) a clean `GPUOutOfMemoryError` (the good path; seen on Linux/Vulkan), (2) `device.lost` (Windows D3D12, seen in at least some Chrome versions), (3) the tab or GPU process crashing (seen on Android). Only (1) gives a clean ceiling. (2) costs a fresh `requestDevice`. (3) is user-visible damage.
- On unified-memory Macs and integrated GPUs, a walk-to-OOM probe measures something closer to "how much system RAM can I take before the OS pushes back", and it can push the machine into swap or memory pressure before any error comes back. The ceiling depends on what else is running and is not a stable device property. Discrete GPUs on Windows can oversubscribe VRAM through WDDM paging into system memory, so allocations may succeed past physical VRAM and the error may never fire. This fits the 31.75 GB figure, which is above any consumer VRAM. [Inference from the cited behaviour; WDDM oversubscription itself was not separately sourced here.]
- Recommended mitigations: probe in a Worker or with awaits between steps (the #6957 filer saw main-thread stalls), write to each buffer (e.g. `queue.writeBuffer` or a clear pass) so it is committed, cap the probe at the largest candidate model's need ("does X fit?") instead of walking to OOM, and use a dedicated GPUDevice that is destroyed afterwards.

### Gaps
- I found no documented per-origin or per-renderer WebGPU memory quota in Chrome's GPU process. Whether Dawn applies any budget (e.g. via `VK_EXT_memory_budget` / DXGI `QueryVideoMemoryInfo`) before reporting OOM was not confirmed.
- Whether a device loss caused by one tab's OOM affects other tabs (shared GPU process, or full GPU process restart when the D3D device is removed) is not documented in what I found. The crbug 40941407 title ("GPU connection lost") suggests process-level loss in that case, which would hit every WebGPU/WebGL context in that GPU process. This needs a real-machine test.
- Safari and Firefox OOM behaviour was not found in any source.

## 3. Does any library already probe GPU memory? (web-llm, transformers.js, demos, fingerprinting)

### Takeaway
No major library probes GPU memory. web-llm ships a static `vram_required_MB` per model but never compares it to the device. It only checks feature flags (`shader-f16`) and buffer-binding limits. transformers.js only checks `shader-f16`. The only known "walk to OOM" prober is the individual developer who filed gpuweb #6957. Fingerprinting research targets timing and contention side channels. I found none that uses OOM-based capacity probing, though the #6957 filer and the spec both flag it as a leak.

### Cited Findings
- web-llm `ModelRecord` fields: `vram_required_MB` ("amount of vram in MB required to run the model (can use `utils/vram_requirements` to calculate)"), `low_resource_required` ("whether the model can run on limited devices (e.g. Android phone)"), `buffer_size_required_bytes` ("required `maxStorageBufferBindingSize`, different for each device"), and `required_features` (e.g. shader-f16). Sample values: Llama-3.2-1B q4f16 879 MB (low_resource true), Llama-3.1-8B q4f16 5001 MB, Phi-3.5-mini q4f16 3672 MB, Qwen3-0.6B q4f16 1403 MB, gemma-4-E2B q4f16 3387 MB. — [web-llm src/config.ts](https://github.com/mlc-ai/web-llm/blob/main/src/config.ts)
- In the web-llm clone (2026-10-11), `vram_required_MB` appears only in config.ts and a record-equality helper in utils.ts. **No runtime code compares it to device capacity.** `utils/vram_requirements` computes it offline from the compiled model's wasm `_metadata` function, so it is a static estimate (params plus workspace plus KV cache), not a measurement. — [web-llm repo](https://github.com/mlc-ai/web-llm) (`src/utils.ts`, `utils/vram_requirements/src/vram_requirements.ts`)
- web-llm runtime checks: `tvmjs.detectGPUDevice()` (throws `WebGPUNotAvailableError` if no device); for each `required_features` entry, `device.features.has()`, throwing `ShaderF16SupportError` or `FeatureSupportError`; `llm_chat.ts` throws `ArtifactManifestError` if the compiled artifact's `max_storage_buffer_binding_size` exceeds the device's; `engine.ts` warns if maxStorageBufferBindingSize < 1 GB, listing the "-1k" context models that may still work; `device.lost` handler unloads and throws `DeviceLostError` if loss happens during reload. The public API `getMaxStorageBufferBindingSize()` is documented as usable "to guess whether the device has limited resources like an Android phone". `getGPUVendor()` returns e.g. arm, qualcomm, apple. — [web-llm src/engine.ts, src/llm_chat.ts, src/types.ts](https://github.com/mlc-ai/web-llm/tree/main/src)
- TVM's `detectGPUDevice` (used by web-llm) calls `requestAdapter({powerPreference: "high-performance"})`, requests maxBufferSize 1 GB and falls back to 256 MB, requests maxStorageBufferBindingSize 1 GB and falls back to 128 MB, and requires 32 KB workgroup storage. No memory probe. — [apache/tvm web/src/webgpu.ts](https://github.com/apache/tvm/blob/main/web/src/webgpu.ts)
- transformers.js (2026-10-06): `isWebGpuFp16Supported()` does `navigator.gpu.requestAdapter()` then `adapter.features.has('shader-f16')`, and session creation throws "The device (webgpu) does not support fp16" if an fp16 dtype is picked without it. `device: 'auto'` simply returns all supported execution providers in order, and `'gpu'` filters to webgpu/cuda/dml/webnn-gpu. No memory or capacity check. — [transformers.js packages/transformers/src/utils/dtypes.js, models/session.js, backends/onnx.js](https://github.com/huggingface/transformers.js)
- WebGPU-SPY (Ferguson, Wilson, Naghibijouybari, ASIA CCS 2024): a GPU cache side channel built from WebGPU compute with a GPU-hardware timer, about 90% precision fingerprinting the top 100 websites on Intel iGPUs. — [arXiv 2401.04349](https://arxiv.org/pdf/2401.04349); [ACM DL](https://dl.acm.org/doi/10.1145/3634737.3637648)
- LockedApart: faster GPU fingerprinting through the WebGPU compute API by measuring thread contention, described as faster and more accurate than DrawnApart. — [LockedApart poster](https://tosc.iacr.org/index.php/uASC/article/download/12008/11879)
- Hohentanner et al., "Unveiling Privacy Risks in WebGPU through Hardware-based Device Fingerprinting", WiSec 2025 (DOI 10.1145/3734477.3734700). Full text not retrieved. — [cited via ACM record of WebGPU-SPY](https://dl.acm.org/doi/10.1145/3634737.3637648)
- "What Browsers Do in the Shaders" (arXiv 2606.26412, 2026): the clearest leak is persistent pipeline-cache state. Other resource probes (bandwidth, queue progress) were "measurable but weaker" (AUROC 0.66-0.80). Metadata bucketing is one defense family. In a crawl of 7,477 successful page loads, only 56 showed any WebGPU evidence and 32 were adapter-probe-only. The paper does **not** study memory-capacity or OOM probing. — [arXiv 2606.26412v1](https://arxiv.org/html/2606.26412v1)
- Brave scrubs WebGPU adapter vendor/architecture/device as part of its GPU fingerprinting protections. — [Brave privacy update #38](https://brave.com/privacy-updates/38-webgl-webgpu-fingerprinting-protections/)

### Inferences
- modelfit's probing allocator would be new as a packaged library feature. web-llm's static `vram_required_MB` table is the closest prior art for the dataset side. modelfit could use those numbers as the "model need" input, and web-llm users (e.g. WebLLM chat) currently find out at load time through OOM or device loss.
- Privacy: a walk-to-OOM probe gives a high-resolution, load-dependent number. That is exactly what the spec's §2.1.11 warns about and what the #6957 filer called more leaky than a bucket. Browsers could reasonably start to quantize or rate-limit OOM behaviour later, and privacy browsers (Brave, Tor) already scrub adapter info. modelfit should quantize its own result (e.g. to 1 GB buckets), never send it anywhere (this already matches the "never sends data about the user" rule), and use a "does model X fit" threshold test instead of a full walk.

### Gaps
- I found no public "WebGPU memory test" demo page beyond the #6957 description. One may exist; a GitHub code search for `pushErrorScope("out-of-memory")` loops was not possible because the GitHub MCP connector failed in this session.
- MediaPipe / LiteRT web and ONNX Runtime Web fit-check logic was not inspected. Neither is known to do a memory check, but this is unverified.

## 4. navigator.deviceMemory, hardwareConcurrency, navigator.gpu availability

### Takeaway
`navigator.deviceMemory` is Chromium-only and coarse. A January 2026 blink-dev intent moves its buckets to 2/4/8 (Android) and 2/4/8/16/32 (desktop). It reports system RAM, not VRAM. Real-world WebGPU usage is still tiny.

### Cited Findings
- Intent to Ship "Update Device Memory API limits" (Barry Pollard, 2026-01-19): new values are 2, 4, 8 on Android and 2, 4, 8, 16, 32 elsewhere, replacing 0.25/0.5/1/2/4/8. The aim is to lower low-end fingerprinting risk and allow high-end segmentation. Android stays capped at 8 because ">8GB RAM is still rare for mobile". Shipped behind a feature flag for revertibility. — [blink-dev intent](https://groups.google.com/a/chromium.org/g/blink-dev/c/vXtAmrVZeDk/m/kO39WH6NAwAJ)
- MDN now documents values 2, 4, 8, 16, 32 and says bounds may change. — [MDN Navigator.deviceMemory](https://developer.mozilla.org/docs/Web/API/Navigator/deviceMemory)
- The Device Memory API is non-standard / Chromium-only (no Firefox or Safari). — [kainino0x on gpuweb #5505](https://github.com/gpuweb/gpuweb/issues/5505)
- WebGPU page-load prevalence: about 0.75% of 7,477 crawled pages had any WebGPU evidence, mostly `requestAdapter` probing. — [arXiv 2606.26412v1](https://arxiv.org/html/2606.26412v1)

### Inferences
- On integrated or unified-memory devices, deviceMemory (rounded system RAM, capped at 32 on desktop and 8 on Android) plus Chrome's own heuristic (iGPU VRAM ≈ max(heap, RAM/2)) is a cheap, non-invasive prior. Coupled with a vendor/architecture hint, it may get most of the way without a probe.

### Gaps
- Whether the deviceMemory change has reached Chrome stable (and which version) was not confirmed.
- No reliable global figure for the share of users with a working `navigator.gpu` was found. `hardwareConcurrency` caps and behaviour (e.g. Safari clamping) were not researched in time.

## 5. Chrome built-in AI (Prompt API / Gemini Nano) qualification

### Takeaway
Chrome decides eligibility in a privileged process with native APIs, not with web-visible probing. It reads the GPU heap size and runs a short inference benchmark, then bins the device into a performance class. The hard VRAM floor in code is 3000 MiB (integrated GPUs credited with at least half of system RAM). Public docs say "strictly more than 4 GB VRAM", or CPU with 16 GB RAM and 4 cores. Web pages see only `LanguageModel.availability()`, which is a strong precedent for a tri-state fit answer.

### Cited Findings
- Public requirements: GPU "strictly more than 4 GB of VRAM", or CPU with 16 GB RAM or more and 4 or more cores. Audio input needs a GPU. At least 22 GB free on the profile volume. Windows 10/11, macOS 13+, Linux, ChromeOS on Chromebook Plus; no Android or iOS. Unmetered network. `LanguageModel.availability()` reports readiness; debug through `chrome://on-device-internals`. — [Chrome docs: Get started with built-in AI](https://developer.chrome.com/docs/ai/get-started); [Prompt API](https://developer.chrome.com/docs/ai/prompt-api)
- Chromium `performance_class.cc`: inputs are a benchmark's `input_speed`/`output_speed` (tokens/s), `is_integrated_gpu`, `device_heap_size` and `max_buffer_size`. For integrated GPUs, `device_heap_mb = max(system_ram/2, device_heap_mb)`. Thresholds (Finch-tunable FeatureParams, defaults): `on_device_low_ram_threshold_mb` 3000 (below it, kVeryLow with reason kLowRAM); output speed < 5 tok/s gives kVeryLow; input speed < 50 kVeryLow, < 75 kLow, < 200 or heap < `on_device_high_ram_threshold_mb` 5500 gives kMedium, < 500 kHigh, else kVeryHigh. — [Chromium source: services/on_device_model/ml/performance_class.cc](https://chromium.googlesource.com/chromium/src/+/main/services/on_device_model/ml/performance_class.cc)
- `optimization_guide_features.cc`: `compatible_on_device_performance_classes` default "3,4,5,6", `compatible_low_tier_on_device_performance_classes` "3,4", and a separate class list for image input. There is a feature `kOnDeviceModelFetchPerformanceClassEveryStartup`. — [Chromium source: components/optimization_guide/core/optimization_guide_features.cc](https://chromium.googlesource.com/chromium/src/+/main/components/optimization_guide/core/optimization_guide_features.cc)
- A hands-on investigation shows `chrome://on-device-internals` listing "Minimum VRAM required (MiB): 3000" next to "Detected VRAM (MiB): 24326". Edge stores `performance_class` and `vram_mb` under `optimization_guide.on_device` in Local State. The enterprise policy `GenAILocalFoundationalModelSettings`=1 blocks the download (Chrome 124+). — [dev.to investigation](https://dev.to/jacquesgariepy/inside-chromes-edges-silent-4gb-ai-install-a-complete-hands-on-investigation-54g2)
- A third-party write-up maps class numbers as 2 = VeryLow/CPU, 4 = Medium, 6 = VeryHigh, and mentions a flag to force or bypass the perf requirement. — [flaming.codes guide](https://flaming.codes/posts/chrome-gemini-nano-built-in-ai) (secondary; not verified against the mojom enum)

### Inferences
- The gap between code (3000 MiB floor) and docs (>4 GB) suggests docs are conservative or a different gate applies to the web APIs. The dev.to author reads it as "3-4 GB devices may have the model on disk but cannot call the open-web APIs" (unverified).
- Precedent for modelfit: (1) combine a memory floor with a *measured speed benchmark*, not memory alone; (2) treat integrated GPUs as max(reported heap, RAM/2); (3) expose a coarse result to pages (`available` / `downloadable` / `unavailable`), never raw VRAM. Chrome itself avoids exposing the number, which supports modelfit quantizing its output. Chrome can only do this because it reads native heap sizes in the browser process. Web code cannot, which is why a probe is needed at all.

### Gaps
- The exact `PerformanceClass` mojom enum numbering was not fetched from source.
- How Chrome measures `device_heap_size` per backend (DXGI dedicated memory vs. Metal recommendedMaxWorkingSetSize vs. Vulkan heap) was not traced past the comment quoted above.

## 6. Risks: device loss across tabs, performance cost, mobile

### Takeaway
The main risks are an ungraceful failure (device loss or GPU-process loss on Windows D3D12, crashes on Android), main-thread stalls and memory pressure on unified-memory machines, and the fingerprinting optics. Mobile is the riskiest platform and the least useful one to probe.

### Cited Findings
- Windows D3D12: VRAM exhaustion produced "GPU connection lost" instead of GPUOutOfMemoryError (M114+). — [crbug 40941407](https://issues.chromium.org/issues/40941407) (snippet)
- Android: Chrome crashed when creating too many WebGPU buffers. — [crbug 41492442](https://issues.chromium.org/issues/41492442) (snippet)
- The walk-to-OOM probe "stalls the main thread" and puts pressure on the GPU (practitioner report). — [gpuweb #6957](https://github.com/gpuweb/gpuweb/issues/6957)
- Probe results can change before the real allocation, so the maintainer recommends pre-allocating the chosen model's resources before download. — [gpuweb #6957](https://github.com/gpuweb/gpuweb/issues/6957)
- Spec: UAs should consider developer-visible warnings for device losses the app did not start. — [WebGPU spec](https://www.w3.org/TR/webgpu/)
- web-llm marks mobile-viable models with `low_resource_required` and uses maxStorageBufferBindingSize as a phone detector, a cheaper alternative to probing on mobile. — [web-llm config.ts / types.ts](https://github.com/mlc-ai/web-llm/blob/main/src/config.ts)

### Inferences
- Viability verdict: **workable as a bounded "fit test", risky as an unbounded "ceiling probe".** Suggested design: (a) prefilter with adapter vendor/architecture, isFallbackAdapter, limits, `shader-f16`, deviceMemory and the dataset; (b) if needed, run one threshold test that allocates and touches up to the largest candidate's `vram_required_MB` plus headroom, in a dedicated device, stepping in ~256-512 MB chunks inside `out-of-memory` error scopes, listening to `device.lost`, then destroying everything; (c) skip the probe entirely on Android/iOS and on devices with deviceMemory ≤ 4; (d) report the result as `measured` only when the threshold test passed, otherwise `similar-hardware` / `estimate`; (e) recommend pre-allocation before download as the final check.
- Before shipping, test on real machines: Windows D3D12 discrete NVIDIA/AMD (does it OOM or lose the device; does it affect other tabs), Intel/AMD iGPU, Apple Silicon (swap pressure, Safari 26 vs Chrome), Linux Vulkan, Android Chrome, iOS Safari. This follows the repo's "measure, don't assume" rule.
