# Crowded field leaves one narrow opening

**Verdict: the space is partly open, not wide open.** As of October 2026 the end-user question "what can my computer run?" is solved several times over, and the measured, crowdsourced dataset that `docs/PLAN.md` calls "the product" already exists in three places. The leader, [llmfit](https://github.com/AlexsJones/llmfit) (Rust, MIT, about 38k stars), detects hardware, ranks models across Ollama, llama.cpp, MLX, LM Studio and Docker Model Runner, labels each answer as measured locally, measured by the community or estimated, and ships **497 community benchmark submissions across roughly 48 hardware types** inside every release ([community data folder](https://github.com/AlexsJones/llmfit/tree/main/llmfit-core/data/community)). A separate site, [LocalMaxxing](https://localmaxxing.com/en), shows **9,263 measured runs on 650 hardware configurations**. What nobody ships is the developer-facing shape modelfit proposes: a **one-call, in-process library on npm and PyPI that takes the app developer's own shortlist**, answers across independent runtimes including the browser, and returns a stable, documented result. That gap is real but narrow, because llmfit already has a Rust library crate and could add bindings. The name is not available: crates.io `modelfit` is taken by a crate with the same purpose, PyPI `modelfit` is taken, npm `modelfit` is almost certainly blocked, and modelfit.io is a competing product. The plan should go ahead only as a thin, embeddable picker that **consumes existing measured data rather than racing to collect its own**, under a new name, with the browser probe redesigned as a bounded fit test.

## What is still open, and what is already taken

The useful way to read the landscape is to split modelfit into its parts and ask who already owns each one. Hardware detection, memory estimation and "does this one model fit" are commodities. llama.cpp now auto-fits a model to free device memory by default with `--fit` ([llama-cli man page](https://dyn.manpages.debian.org/testing/llama.cpp-tools/llama-cli.1.en.html)), LocalAI deleted its own VRAM estimator because "this is now handled directly in llama.cpp" ([LocalAI commit mirror](https://gitea.varghacsongor.hu/GithubMirror/LocalAI/commit/800f749c7ba2fdefce6270fc22167a256a418983)), and gguf-parser-go claims GGUF memory estimates within about 100 MiB ([GitHub](https://github.com/gpustack/gguf-parser-go)). Ranking a catalogue for an end user, with a measured-vs-estimated label, is owned by llmfit. A crowdsourced measured dataset is owned, at increasing scale, by LocalScore, llm-speed, llmfit's community folder and LocalMaxxing.

**Still open** are four things, and they only count together. First, an **in-process import API in JavaScript and Python**: llmfit's PyPI package is a launcher for the Rust binary (its `__init__.py` only exposes `find_llmfit_bin()`, [source](https://github.com/AlexsJones/llmfit/blob/main/llmfit-python/src/llmfit/__init__.py)), and no llmfit npm package exists ([GitHub](https://github.com/AlexsJones/llmfit)). Second, a **developer-supplied shortlist** as the primary input; every tool found ranks its own catalogue. Third, **cross-runtime choice that includes browser runtimes** (WebLLM, transformers.js, Chrome built-in AI); searches for any such recommender found none ([localmodel.run tools list](https://localmodel.run/tools)). Fourth, a **stable, documented answer contract** an app can depend on. The closest JS building block, node-llama-cpp, scores how well one GGUF fits and returns RAM and VRAM use, but gives no tokens per second and has no "pick from a list" call ([ConfigurationResolver API](https://node-llama-cpp.withcat.ai/api/classes/GgufInsightsConfigurationResolver)).

No funded startup sells device-aware local model selection as its product. Adjacent companies build on-device inference stacks, such as Mirai with a $10M seed ([TechCrunch](https://techcrunch.com/2026/02/19/co-founders-behind-reface-and-prisma-join-hands-to-improve-on-device-model-inference-with-mirai/)) and Cactus from YC S25 ([InfoQ](https://infoq.com/news/2025/12/cactus-on-device-inference/)). The realistic threats are llmfit adding bindings, Hugging Face turning its per-quant hardware compatibility panel into an API (it already exposes users' saved hardware through OAuth `hardwareItems`, [HF docs](https://huggingface.co/docs/hub/main/hardware.md)), and SDK vendors adding a size picker.

## llmfit already shares measured data across machines

The research notes disagreed on this point, and the source settles it in favour of the end-user note. llmfit's README states that you can "contribute the results back to the project as a PR, straight from the TUI", and that "each merged submission ships in the next release: anyone on identical hardware gets measured ✓ numbers before they ever run a benchmark" ([README](https://raw.githubusercontent.com/AlexsJones/llmfit/main/README.md)). The community README describes the mechanism: `llmfit bench --all --share` shows the exact JSON payloads, asks for confirmation, authenticates through the GitHub device flow and opens a pull request into `llmfit-core/data/community/<hardware-slug>/`, where a CI workflow validates the schema and checks "measurements within physical limits for the reported hardware" before merge ([community README](https://github.com/AlexsJones/llmfit/blob/main/llmfit-core/data/community/README.md)). Runs made without `--share` stay in a local store. The confidence ladder in the method doc includes `measured_community`, defined as "Benchmarked by others on hardware matching this machine" ([how-it-works](https://github.com/AlexsJones/llmfit/blob/main/docs/how-it-works.md)), and the precedence is "your own runs > llmfit community on identical hardware > localmaxxing medians on matching presets > formula estimate" ([CLI docs](https://github.com/AlexsJones/llmfit/blob/main/docs/cli.md)).

Counting the repository tree on 2026-10-18 gives **497 submission files in about 48 hardware folders**, submitted between 10 July and 11 October 2026 ([repo tree](https://github.com/AlexsJones/llmfit/tree/main/llmfit-core/data/community)). The distribution is lopsided: two Intel integrated-graphics folders hold 290 of the files, Apple M2 Pro has 34, and most discrete GPUs have between one and nine, with some duplicate slugs for the same card. llmfit also embeds a scraped `benchmark_cache.json` from LocalMaxxing (scraped 2026-10-12) with **1,411 rows across 27 hardware presets**, from which it takes medians ([data file](https://github.com/AlexsJones/llmfit/blob/main/llmfit-core/data/benchmark_cache.json); [TUI guide](https://github.com/AlexsJones/llmfit/blob/main/docs/tui.md)). Matching is on "identical hardware (same CPU + GPU)", so there is no documented "similar hardware" tier between exact match and formula, which is one place modelfit's §5.6 fallback still adds something.

Two other details matter for embedding. The `llmfit-core` crate is a real library: `lib.rs` re-exports `build_model_fits(db, specs, installed, context_limit, forced_runtime)`, `SystemSpecs`, `ModelFit` and `EstimateConfidence` ([lib.rs](https://github.com/AlexsJones/llmfit/blob/main/llmfit-core/src/lib.rs); [analysis.rs](https://github.com/AlexsJones/llmfit/blob/main/llmfit-core/src/analysis.rs)). A Rust developer could pass a filtered `ModelDatabase` and get a ranked shortlist today, although only about half the crate is documented and there are no examples ([docs.rs](https://docs.rs/crate/llmfit-core/latest)). The REST server already returns `estimated_tps`, `estimate_confidence`, `measured_tps` and a `verify_command` per model ([API.md](https://github.com/AlexsJones/llmfit/blob/main/API.md)), which is close to modelfit's planned `source` field.

## Measured data exists at scale, and it is not modelfit.io's

The plan assumed the dataset would be the moat. Four public collections now exist, and the largest dwarfs anything llm-bench could gather in a year. **LocalMaxxing** reports 2,772 users, 9,263 runs, 650 hardware configurations and 825 models run, with every number "from a community-submitted run on real hardware" ([LocalMaxxing](https://localmaxxing.com/en)). It is run by the account @lottolabs, its site code is MIT, and it gives no open data licence; CSV and JSON leaderboard export is a $9.99 a month Pro feature ([Pro](https://localmaxxing.com/en/pro); [Terms](https://localmaxxing.com/en/terms)). **llm-speed** (CLI by GitHub user meadow-kun, [PyPI](https://pypi.org/pypi/llm-speed/json)) signs each run and says its open dataset holds "522 measured results from 277 public runs across 71 models and 28 hardware configurations" ([llm-speed.com](https://llm-speed.com)); its Hugging Face mirror is CC BY 4.0 but has not been refreshed since July and shows 220 rows ([HF dataset](https://huggingface.co/datasets/llmspeed/llm-speed-benchmarks)). **llmfit's community folder** is described above. **LocalScore** is small and fixed to three models on llamafile ([localscore.ai](https://www.localscore.ai/)). Outside the crowdsourced sites, OpenBenchmarking's `pts/llama-cpp` profile is very active but fragments across builds, with tens to a few hundred results per configuration ([OpenBenchmarking](https://mail.openbenchmarking.org/test/pts/llama-cpp)), and the llama.cpp Vulkan discussion has about 130 curated scoreboard rows for one model ([GitHub #10879](https://github.com/ggml-org/llama.cpp/discussions/10879)).

**modelfit.io's "open CC BY 4.0 dataset" is not a measured dataset and is not the same as llm-speed's or llmfit's.** It is published by the GitHub account Wecko-ai (profile "Creator of ModelFit", created 2026-06-15) and holds **156 model rows (116 local, 40 cloud, 27 families)**, updated 2026-10-13 ([models.json](https://github.com/Wecko-ai/modelfit-hardware-dataset/blob/HEAD/models.json); [Wecko-ai](https://github.com/Wecko-ai)). Each row is a model with a quantisation, a minimum RAM, an estimated load and an `ollama run` command. Its README is explicit: fit means estimated load within about 70 to 85 percent of memory, at "roughly 0.6 GB per billion parameters", and "memory-load and tokens/sec figures are estimates, not measured benchmarks" ([README](https://github.com/Wecko-ai/modelfit-hardware-dataset)). It is a model catalogue, not a hardware dataset, and so it competes on the name and the pitch rather than on data.

The gaps in this data are where modelfit's measurement still counts. No public dataset measures the **same model on the same machine across several runtimes**, which matters because Ollama's move to MLX on Mac nearly doubled decode speed for one model, from 58 to 112 tok/s ([Level Up Coding](https://levelup.gitconnected.com/ollama-mlx-nearly-doubles-llm-speed-on-your-mac-58-to-112-tok-s-and-your-old-models-get-none-of-fd1a9ec531fb)). No downloadable cross-device **WebGPU / WebLLM** dataset exists ([LlamaWeb paper](https://www.alphaxiv.org/abs/2605.20706) has four GPUs). And none of the collections is keyed on **free memory at the moment of choice**. Signing also is not a moat: llm-speed itself says "signing records provenance, not independent hardware verification" ([llm-speed.com](https://llm-speed.com)), and Geekbench's history of spoofed device identities shows why ([XDA](https://www.xda-developers.com/xiaomi-poco-f1-lite-fake-benchmark/)).

## Runtimes fit one model; none chooses between runtimes

Every major runtime is now hardware-aware for its own engine. LM Studio labels each quantisation by GPU offload feasibility and offers `lms load --estimate-only` ([LM Studio docs](https://lmstudio.ai/docs/cli/local-models/load)), though one estimate was double the real use ([lms #499](https://github.com/lmstudio-ai/lms/issues/499)). Ollama measures exact memory before loading since v0.12 and sizes the default context by VRAM tier, but recommends no model ([Ollama docs](https://docs.ollama.com/context-length)). Jan shows "Fits / May be slow / Won't fit" style labels ([StorageReview](https://www.storagereview.com/review/jan-v0-8-6-hands-on-running-local-llms-on-windows)). Foundry Local picks a CUDA, NPU or CPU **variant of one model** with "zero detection code required" ([GA blog](https://devblogs.microsoft.com/foundry/foundry-local-ga/)). Chrome, Apple and Windows only gate a single built-in model on hard thresholds, such as Chrome's "strictly more than 4 GB of VRAM" or 16 GB RAM with 4 cores ([Prompt API](https://developer.chrome.com/docs/ai/prompt-api)).

The plan's line that "a runtime can't recommend across runtimes" is half true. Msty already routes users to "the engine that makes the most sense for your setup", MLX on Apple Silicon and Ollama or llama.cpp elsewhere ([Msty blog](https://msty.ai/blog/one-model-hub/)), and LM Studio and Ollama each bundle llama.cpp and MLX engines. The defensible version is narrower: no tool recommends across **independent** runtimes from measured per-runtime data, none includes browser runtimes, and none is embeddable in a third-party app. The platform gates also create demand: an app that tries Chrome's built-in model or Apple's needs a fallback picker when `availability()` says no.

## Browsers still hide GPU memory, and the spec editors endorse probing

The standard WebGPU API exposes no memory capacity. `GPUAdapterInfo` carries vendor, architecture, device and description strings that browsers may leave empty ([WebGPU spec](https://www.w3.org/TR/webgpu/)); by default Chrome returns only vendor and a coarse architecture family, with device and description filled only under the developer-features flag ([Chromium gpu_adapter.cc](https://chromium.googlesource.com/chromium/src/+/main/third_party/blink/renderer/modules/webgpu/gpu_adapter.cc)). Chrome's non-standard `memoryHeaps` sits behind that same flag ([Chrome developer features](https://developer.chrome.com/docs/web-platform/webgpu/developer-features)). The working group has twice declined a memory-capacity signal: #5505 (January 2026, still open at "Milestone 4+") and #6957, **closed as not planned on 2026-09-24**, where the maintainer advised trial allocations plus allocating and touching the model's buffers before download ([gpuweb #5505](https://github.com/gpuweb/gpuweb/issues/5505); [gpuweb #6957](https://github.com/gpuweb/gpuweb/issues/6957)). `navigator.deviceMemory` is Chromium-only, reports system RAM, and is moving to buckets of 2, 4, 8, 16 and 32 on desktop and a cap of 8 on Android ([blink-dev intent](https://groups.google.com/a/chromium.org/g/blink-dev/c/vXtAmrVZeDk/m/kO39WH6NAwAJ)).

So the probing allocator in §5.1 is aligned with what the spec authors recommend, and no major library does it: WebLLM ships a static `vram_required_MB` per model and never compares it with the device, and transformers.js only checks `shader-f16` ([web-llm config.ts](https://github.com/mlc-ai/web-llm/blob/main/src/config.ts); [transformers.js](https://github.com/huggingface/transformers.js)). CanIRun.ai sidesteps the problem by guessing from the GPU name plus a spec table ([runaihome review](https://runaihome.com/blog/canirun-ai-local-llm-hardware-checker-review-2026/)). The risks are concrete, though. On Windows D3D12, exhausting VRAM has produced "GPU connection lost" instead of a catchable out-of-memory error ([crbug 40941407](https://issues.chromium.org/issues/40941407), detail from a search snippet), Chrome on Android has crashed on too many buffers ([crbug 41492442](https://issues.chromium.org/issues/41492442)), and the #6957 filer reports that a walk-to-OOM probe "stalls the main thread" and that it "leaks more than a bucketed number would". On unified memory and under Windows paging, an untouched allocation may succeed without being resident, so a ceiling probe measures system pressure as much as capacity. Chrome's own model gate shows the better pattern: it reads native heap sizes, credits integrated GPUs with at least half of system RAM, runs a short speed benchmark and exposes only a coarse class ([Chromium performance_class.cc](https://chromium.googlesource.com/chromium/src/+/main/services/on_device_model/ml/performance_class.cc)). The verdict is that the probe is **workable as a bounded "does candidate X fit" test and risky as an unbounded ceiling walk**.

## Recommended changes to Phase 0 and later phases

Phase 0 should add three checks to its existing ones. The first is a **build-or-build-on test**: embed `llmfit-core` in a ten-line Rust program, pass a three-model shortlist, and compare its answers and its `measured_community` hits with llm-bench on Goose and the other Phase 0 machines. If llmfit's ranking is good, modelfit becomes a binding and contract layer over it (or a contribution upstream); if it is not, the comparison shows exactly where modelfit's ranking must be better. The second is a **data access decision**: confirm reuse terms for llmfit's community JSON (it sits in an MIT repository, but data licensing should be confirmed with the maintainer), llm-speed (CC BY 4.0) and LocalMaxxing (no open licence, paid export, so ask before using). The third is **demand validation**: talk to at least five developers who ship local models in Electron, Tauri or WebLLM apps and ask whether they would add a dependency for this, and what answer shape they need. The browser prototype should be re-scoped to the bounded fit test above and must record the three failure outcomes on Windows D3D12 discrete, an integrated GPU, Apple Silicon under Safari and Chrome, and Linux Vulkan, plus whether a device loss in one tab affects others. The rename belongs in Phase 0, before any repository, package or domain is created.

Later phases should shift weight accordingly. **Phase 1** should start by ingesting existing open measurements into the result schema, and narrow `llm-bench --share` to the gaps: cross-runtime pairs and free-memory context. **Phase 2** should reuse MIT heuristics from llmfit with attribution where they hold up, and add the "similar hardware" tier that llmfit lacks. **Phase 3** should ship npm first, since JavaScript has no picker beyond node-llama-cpp's single-model score and no llmfit package. **Phase 5** deserves to move earlier, or at least to be prototyped in parallel with Phase 3, because the browser is the one runtime where no competitor offers anything beyond a GPU-name lookup and WebLLM users currently discover a bad fit only at load time. **Phase 6**'s public "what can my computer run" page should be dropped or reduced; that page is the most crowded part of the whole landscape.

## Conclusion

The research turns modelfit from a data company into an integration company. The measurements, the estimators and the user-facing recommenders all exist; what does not exist is the piece an app developer would actually import, with their own model list, in their own language, including the browser. That is a smaller product than PLAN.md describes, cheaper to build, and less defensible, so speed and a clean contract matter more than collection volume. The single most informative experiment is cheap: try to build modelfit's `pick()` on top of `llmfit-core` and the open datasets in Phase 0. If that works, the honest plan is a thin, well-documented layer (or an upstream contribution); if it fails, the failure will name the differentiation.

Unknowns remain. Download numbers for the competing packages were not collected, Safari and Firefox WebGPU out-of-memory behaviour is undocumented, LocalMaxxing's API terms for third-party apps are unclear, and no trademark search has been run on `pickmodel`. Each of these is a Phase 0 measurement, not a reason to wait.
